# Epic 1 — Namespace Data Model: Design Document

Captured from design session 2026-03-24.

---

## Core principle

`namespace_id` (UUID) is the single axis of data separation across the entire system.
Every vector in Qdrant, every document in the docstore, every file in MinIO belongs to exactly
one namespace. All downstream services (worker, indexing, parsing) receive `namespace_id` and
nothing else — they are unaware of ownership, type, or display concerns.

---

## Namespace types

| Type | What it represents | ID generation | Owner |
|---|---|---|---|
| `PRIVATE` | One user's chat session. `chat_id` is a `namespace_id` — `chat_id` ceases to be a separate concept. | UUID4 (random, generated by storage service) | Zitadel user subject |
| `SHARED` | An enterprise project / library, shared across users belonging to an org. | UUID5 derived from natural name (e.g. `uuid5(ARTEMIS_NS, "OpenTitan")`) | Zitadel org ID |

---

## Database schema

### `namespace`

```sql
id           UUID         PRIMARY KEY              -- the namespace_id
name         TEXT         NOT NULL                 -- display label; UUID5 seed for SHARED
type         namespace_type NOT NULL               -- 'private' | 'shared'
owner_id     UUID         NOT NULL                 -- Zitadel sub (PRIVATE) or org ID (SHARED)
                                                   -- no FK — identity is managed externally
created_at   TIMESTAMPTZ  NOT NULL DEFAULT now()
updated_at   TIMESTAMPTZ  NOT NULL DEFAULT now()
```

**Display name notes:**
- `SHARED`: `name` = natural language project name ("OpenTitan") — this is the UUID5 seed AND
  the display label. Non-negotiable, always set by the enterprise connector.
- `PRIVATE`: `name` is set by the frontend at creation, or auto-generated by the storage service
  (e.g. `"Chat · 2026-03-24 14:30"`) if omitted. Renameable via `PATCH /namespaces/{id}`.

### `ingested_file`

```sql
id           UUID         PRIMARY KEY
namespace_id UUID         NOT NULL  REFERENCES namespace(id)
task_id      UUID         NOT NULL  -- FK to apollo_celery_taskmeta; set by JDBC sink
filename     TEXT         NOT NULL  -- extracted from task kwargs
path         TEXT         NOT NULL  -- S3 object key; extracted from task kwargs
content_type TEXT         NOT NULL
size_bytes   BIGINT       NULLABLE
status       TEXT         NOT NULL  -- 'success' | 'failure'; only terminal states
failure_reason TEXT       NULLABLE  -- traceback excerpt on failure
completed_at TIMESTAMPTZ  NOT NULL  -- date_done from Celery result
```

**This table is written exclusively by the CDC pipeline — not by the worker directly.**

Population path:
```
Worker completes task → writes to apollo_celery_taskmeta (Celery's own concern)
    ↓ Debezium CDC (watches status column)
Kafka: artemis.celery.taskmeta
    ↓ filter: status transitions to SUCCESS or FAILURE (terminal only)
JDBC sink → INSERT INTO ingested_file
    (namespace_id, filename, path, content_type from task kwargs JSON)
```

`result_extended=True` is mandatory on the Celery result backend so kwargs are persisted and
available for the CDC pipeline to extract display fields from.

**Two tables, two distinct purposes:**

| Table | Written by | Contains | Used for |
|---|---|---|---|
| `apollo_celery_taskmeta` | Celery / worker | All states (pending → terminal) | Task status polling by `task_id` |
| `ingested_file` | JDBC sink (CDC) | Terminal states only | File list per namespace |

No view joining these tables is needed — they serve orthogonal concerns.

## Service architecture

### Storage Service (`backend-storage`)

Owns: `namespace`, `ingested_file`, `file_ingestion_status` view.

**Single responsibility:** accept file bytes → write to MinIO → record the ingestion event.
Never receives file paths. Never reads from a filesystem. Never knows about Docling or Qdrant.

**Also responsible for:**
- Namespace lifecycle (create, read, rename)
- OpenFGA tuple write on namespace creation (see below)

**REST API:**

```
# Namespace management
POST   /namespaces               create namespace; write OpenFGA tuple
GET    /namespaces               list namespaces owned by caller
GET    /namespaces/{id}          namespace detail
PATCH  /namespaces/{id}          rename (PRIVATE only)
DELETE /namespaces/{id}          soft-delete + trigger file cleanup

# File upload (bytes only — no file paths accepted)
POST   /namespaces/{id}/files    multipart upload; generates task_id; writes ingested_file record

# Observability
GET    /namespaces/{id}/files    paginated file list with ingestion status
GET    /namespaces/{id}/tasks    all tasks for a namespace
GET    /tasks/{task_id}          single task detail (status, failure_reason, retries)
```

### Enterprise Ingest Module (`backend-enterprise-ingest`)  — NEW

Separate FastAPI service. **Only this service** has the enterprise filesystem volume mounted.

**Responsibility:** adapt "file metadata + FS path" (from Kafka HTTP sink) into "bytes POST to
storage service."

```
Kafka HTTP Sink → POST /enterprise/ingest
  body: {
    path: "/mnt/data/opentitan/spec.pdf",   # FS path to read
    filename: "spec.pdf",
    content_type: "application/pdf",
    namespace: "OpenTitan",                 # natural language key
    owner_id: "<org-uuid>"                  # see Open Questions
  }

Handler:
  1. namespace_id = uuid5(ARTEMIS_NS, namespace_name)
  2. POST /namespaces on storage service  (upsert — storage handles get-or-create)
  3. read file bytes from FS path
  4. POST /namespaces/{id}/files on storage service  (bytes)
```

The enterprise module never touches MinIO, Kafka, or OpenFGA directly.

## Deployment modes

The storage service is **infrastructure-agnostic**. It writes to Postgres only. The same binary
ships in both deployment modes. OpenFGA sync is a deployment concern, not a business logic concern.

### Minimal (open-source)

```
Frontend → API Gateway (minimal) → Storage Service → Postgres + MinIO
               Kafka → Worker → Parsing → Indexing → Qdrant
```

- API gateway is present but enforces minimal policy (routing, rate limiting, auth token
  validation only — no OpenFGA, no RBAC decisions).
- Access control: SQL `WHERE owner_id = :jwt_sub` inside the storage service.
- No Debezium, no OpenFGA.
- For fully trusted / single-user self-hosted deployments: auth may be omitted entirely.

### Enterprise (full)

```
Frontend → API Gateway ──► Storage Service → Postgres + MinIO
               │ (OpenFGA check)                  │
               │                           Debezium CDC
               │                                  ↓
            OpenFGA ◄──── HTTP Sink ◄──── Kafka (artemis.public.namespace)
               Kafka → Worker → Parsing → Indexing → Qdrant
```

- Storage service writes `namespace` row to Postgres — nothing else.
- Debezium watches the `namespace` table, publishes inserts to Kafka.
- Kafka HTTP sink POSTs new tuples to OpenFGA write API.
- API gateway enforces OpenFGA decisions before requests reach the storage service.
- Zero OpenFGA code, config, or dependency in the storage service.

## OpenFGA integration

**Storage service responsibility:** none. It has no OpenFGA client, no OpenFGA URL, no retry
logic for OpenFGA failures. It only writes to Postgres.

**CDC path (enterprise deployment only):**
```
INSERT INTO namespace → Debezium → Kafka topic: artemis.public.namespace
  → HTTP Sink → POST /stores/{store}/write on OpenFGA
    body: {writes: {tuple_keys: [{user: "user:{owner_id}", relation: "owner",
                                  object: "namespace:{id}"}]}}
```

**Access control on `GET /namespaces` (list):**
- Both modes: `WHERE owner_id = :jwt_sub` in SQL covers PRIVATE namespaces.
- Enterprise: API gateway may inject `X-Authorized-Namespaces` header (from OpenFGA
  `ListObjects`) to extend the filter for SHARED namespaces the user is a member of.
  Storage service reads the header if present, ignores it if absent. No code branch needed
  for deployment mode — the header presence/absence drives behaviour.

**SHARED namespace access model:** unresolved — see Open Questions.

## Owner table

A thin physical table. Its purpose is solely to anchor the FK from `namespace.owner_id` and
to serve as the CDC trigger point for the owner-deletion cascade.

```sql
owner
─────────────────────────────────────
id          UUID    PRIMARY KEY       -- external IdP subject or org ID
deleted_at  TIMESTAMPTZ  NULLABLE     -- soft-delete trigger for cascade
```

No display name, no email, no other columns. It is not a user registry.

### Population by deployment mode

| Mode | How owner rows are created | How owner rows are deleted |
|---|---|---|
| **Simple** | Upserted by storage service on `POST /namespaces` (`INSERT ... ON CONFLICT DO NOTHING`) | Soft-deleted via API call; DB trigger cascades |
| **Enterprise** | Projection from IdP: JDBC sink connector reads IdP CDC events → inserts into `owner` table | IdP deletes user/org → JDBC sink removes row → DB trigger cascades |

In simple mode the owner table is not a real registry — it is a set of UUIDs observed creating
namespaces. That is acceptable; simple deployments do not manage multi-tenant ownership at scale.

### Deletion cascade via DB trigger

```sql
CREATE FUNCTION soft_cascade_namespace_on_owner_delete()
RETURNS TRIGGER AS $$
BEGIN
    UPDATE namespace
    SET deleted_at = now()
    WHERE owner_id = OLD.id AND deleted_at IS NULL;
    RETURN OLD;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER owner_soft_cascade
AFTER DELETE ON owner
FOR EACH ROW EXECUTE FUNCTION soft_cascade_namespace_on_owner_delete();
```

Debezium watches `namespace.deleted_at` column. When it transitions `NULL → timestamp`, the
HTTP sink calls `DELETE /namespaces/{id}` on the storage service, which dispatches
`apply_async(delete_namespace, namespace_id)`. The worker handles all downstream cleanup.

### FK constraint

```sql
namespace.owner_id UUID REFERENCES owner(id) ON DELETE RESTRICT
```

`ON DELETE RESTRICT` — not CASCADE. Prevents direct hard-deletion of an owner row while
namespaces reference it. Forces deletion through the application cascade chain (soft-delete
namespaces → worker cleans up → worker hard-deletes rows → owner row can be deleted).

---

## Deletion lifecycle (any namespace)

```
1. Soft-delete namespace (deleted_at = now())     ← storage service or DB trigger
2. Debezium detects deleted_at change             ← infrastructure
3. HTTP sink → DELETE /namespaces/{id}            ← infrastructure
4. Storage service: apply_async(delete_namespace) ← storage service
5. Worker: delete Qdrant vectors                  ← worker
6. Worker: delete MinIO objects (prefix scan)     ← worker
7. Worker: delete record manager entries          ← worker
8. Worker: DELETE FROM namespace WHERE id = :id   ← worker (last)
```

In-flight tasks check `namespace.deleted_at` on start — if set, abort with `skipped` status.

## Ingestion pipeline (both paths converge here)

```
# Manual upload (frontend)
Browser → POST /namespaces/{id}/files (bytes)
        → storage service → MinIO
        → storage service: apply_async(fetch_and_parse, task_id, s3_key, namespace_id, filename)
        → RabbitMQ → Celery worker

# Enterprise streaming
Kafka event (file metadata + FS path) → enterprise-ingest module
  → reads bytes from FS
  → POST /namespaces/{id}/files (bytes)   (same storage service endpoint)
  → identical from here
```

The Kafka → MinIO → Kafka → RabbitMQ chain is eliminated. Storage service dispatches
`apply_async()` directly after MinIO upload. Storage service is the sole dispatcher of all
worker tasks. RabbitMQ remains the broker; Kafka is only used as the enterprise directory
connector notification channel (terminating at the enterprise-ingest module).

## Open questions — all resolved

### ~~OQ-1~~ — RESOLVED: `owner_id` source for enterprise SHARED namespaces

Options A and B are complementary, not alternatives.
- Connector config holds the org name as a plain string (e.g. `"Acme Corp"`). Human-readable,
  no UUID management in connector config.
- SMT injects it into the Kafka message header.
- Enterprise-ingest service derives `owner_id = uuid5(ARTEMIS_NS, org_name)` — same
  deterministic pattern as namespace UUID5 derivation. UUIDs are an application concern only.

### ~~OQ-2~~ — RESOLVED: `task_id` propagation strategy

`task_id` is pre-generated by the storage service, passed to `apply_async(task_id=...)`.
Celery immediately creates a PENDING record in `apollo_celery_taskmeta` with that ID.
The JDBC sink extracts `task_id` from the result record when writing to `ingested_file`.
No worker write-back needed.

### ~~OQ-3~~ — RESOLVED: SHARED namespace access model in OpenFGA

Inherited access via org membership. OpenFGA type model:
```
type user
type org
  relations
    define member: [user]
type namespace
  relations
    define owner: [org]
    define can_access: member from owner
```
Evaluation: `can user:X access namespace:Y?` → `org:Z owner namespace:Y` → `user:X member org:Z`
→ granted. One CDC write per namespace creation. Org membership managed separately in OpenFGA.
No per-user per-namespace tuples for SHARED namespaces.

### ~~OQ-4~~ — RESOLVED: UNIQUE constraint on namespace

`PRIMARY KEY (id)` only. No additional UNIQUE constraints.
- SHARED: UUID5 derivation from same org+name always produces the same UUID — duplicates
  impossible by construction, upsert is idempotent.
- PRIVATE: UUID4 is always unique.
- `name` is a display field only. Two PRIVATE namespaces may share a display name.

### ~~OQ-5~~ — RESOLVED: `GET /namespaces` for SHARED namespaces in stub mode

```sql
SELECT * FROM namespace
WHERE owner_id = :jwt_sub   -- user's own PRIVATE namespaces
   OR type = 'shared'       -- all SHARED namespaces (stub: globally visible)
```

No associative table. Enterprise mode replaces this with OpenFGA group membership evaluation
(`can_access` relation check via `ListObjects`).

## Decisions log

| # | Decision | Rationale |
|---|---|---|
| 1 | `namespace_id` is the single data separation axis | Replaces `private/{chat_id}` + `library/{name}` path strings |
| 2 | `chat_id` is an alias for `namespace_id` of type PRIVATE | Eliminates `chat_id` as a separate concept |
| 3 | SHARED namespace IDs derived via UUID5 from natural name | Deterministic, collision-free, no coordination needed across workers |
| 4 | No `owner_id` on `ingested_file` | Access control resolved via namespace join; no propagation through pipeline |
| 5 | Thin `owner` table (id + deleted_at only); FK `namespace.owner_id → owner.id ON DELETE RESTRICT` | Cascade anchor for CDC chain; not a user registry; populated lazily (simple) or via JDBC sink projection (enterprise) |
| 6 | Celery result table accessed via Postgres view | Celery stays sole writer; view is stable interface; no CDC needed |
| 7 | OpenFGA as PDP; CDC-driven sync in enterprise deployment | Externalizes RBAC from application code entirely; storage service has zero OpenFGA dependency |
| 8 | OpenFGA sync via Debezium CDC → Kafka → HTTP sink (enterprise only) | Storage service is infrastructure-agnostic; same binary for minimal and enterprise deployments |
| 9 | Enterprise ingest = separate service (`backend-enterprise-ingest`) | Storage service never needs FS mount; independently scalable |
| 10 | Storage service upload endpoint accepts bytes only | Unified interface regardless of upload source |
| 11 | Storage service owns `/namespaces` routes | Coherent domain: ingestion lifecycle management |
| 12 | Storage service dispatches `apply_async()` directly; Kafka → worker path eliminated | Removes KSQLDB + sink connector complexity; enables immediate task_id return; storage service is sole task dispatcher |
| 13 | `ingested_file` written by JDBC sink (CDC from Celery result table), not directly by worker | Zero application code for the projection; worker stays unaware of `ingested_file`; single infrastructure-owned write path |
| 14 | Deletion cascade: soft-delete → Debezium → HTTP sink → storage → worker | No DB-level cascade past Postgres boundary; worker always last to act; no orphaned downstream data |
| 15 | Owner upsert on namespace creation (simple mode) | Guarantees DB trigger always has a row to fire on; no cold-start failure |
